# Release consumer upgrade evidence

`scripts/test-release-upgrade.py` exercises the selected 0.3.0 → 0.4.0 upgrade
path. This is release qualification, not a general pre-1.0 API/source/binary
compatibility promise. The version policy in `docs/guide/distribution/Packages.md`
and `specs/BinaryFormat.md` remains authoritative.

## Frozen baseline and candidate

The source baseline is tag `0.3.0`, pinned to commit
`4ed9d44ded085ddccebff943365fb924bd0a3ce5`. A different tag target fails the check.
C# restores published 0.3.0 NuGet packages. SwiftPM consumes a local Git mirror
of that exact source revision, with a test tag representing the release.
The candidate is an archive of the checked-out HEAD commit, not uncommitted
product changes. Candidate packages use the isolated version
`0.4.0-upgrade-test`. No public tag, repository branch or published package is
created or changed. The baseline must be deliberately reviewed when advancing
this release gate; this script does not infer future compatibility promises.

## Checks

Each language uses the existing distribution consumer sources as committed with
each version: the baseline builds the consumer from the 0.3.0 commit, the
candidate the consumer from the tested commit. Breaking pre-1.0 API changes are
therefore checked as the migration that the changelog documents, not as source
compatibility. Each consumer compiles source, serializes and loads it, checks
native integration and expects result 42. Swift additionally
exercises Bridge macros; both full consumers exercise the highlighter.

The same consumer directory then receives the candidate consumer source,
resolves the candidate version, rebuilds and reruns. C# explicitly uses `dotnet build -t:Rebuild`: reproducible package DLLs
can have identical timestamps and sizes across versions, allowing an incremental
CopyLocal step to retain an old assembly. A clean rebuild is part of this tested
minor-version migration; incremental replacement is not claimed by this test.
The script verifies all relevant NuGet assets/SwiftPM resolved pins;
a partial upgrade or stale baseline resolution fails. A separate Runtime
consumer executes the baseline-produced binary first with baseline dependencies
and then with candidate dependencies. This selected binary smoke test does not
extend acceptance guarantees to all pre-1.0 bytecode. Existing canonical binary
fixtures and broad Conformance tests remain independent.

The baseline binary is generated by the actual old compiler on each run and
must match the frozen fixture under `conformance/fixtures/Release030` exactly:

| Fixture | SHA-256 |
|---|---|
| `csharp-consumer.gesb` | `608fc3ef143c2cc60d9d3ac419ead3775fb536c3a734e1b74df37d50c074c87a` |
| `swift-consumer.gesb` | `c281d4025925866c55f72d4a415238e25c872d7d037c826a3b4a3f592cfd19d7` |

These fixtures were produced by the pinned baseline and must not be regenerated
with the candidate compiler. A changed baseline source or binary requires review.
 The
retained summary records its exact base64 bytes, SHA-256, baseline revision,
candidate revision and outcome. Thus the fixture and provenance survive cleanup
and can be replayed independently. This fixture does not freeze arbitrary 0.x
opcode encodings or change the source-recompilation guidance for new features.

## Running and release integration

```sh
python3 scripts/test-release-upgrade-controls.py
python3 scripts/test-release-upgrade.py --language csharp
python3 scripts/test-release-upgrade.py --language swift
```

Requires the baseline tag locally, network access for published NuGet/SwiftSyntax
dependencies, and the normal supported SDKs. Each command uses disposable
workspaces below `artifacts/release-upgrade/<language>`. Success retains top-level
logs in `latest-logs` and removes the build trees; failure preserves its workspace.
Commands have timeouts. Negative controls reject stale/missing package versions,
consumer failures and timeouts. Neither command publishes anything.

The Release Upgrade Validation workflow runs manually or as a prerequisite of
C# Release Candidate, including its nonpublishing dry run. C# and Swift execute
in parallel. It adds no job or build to normal Swift PR CI; ordinary C# CI runs
only the small Python harness controls. Upgrade logs are retained as release
evidence. New language features, exhaustive old-version binary support and
installer upgrade UX are outside this selected consumer smoke test.
