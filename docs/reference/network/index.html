GES network

Since: 0.6.0

This document owns GES network sessions. A network declaration in a schema source names which wire roots a client and a server exchange, and in which delivery class. A session carries the encoded records of those roots between the two sides over a transport: a TCP stream, WebSocket messages, UDP datagrams or the in-process pair. A server with a key of its own encrypts its sessions. The network guide introduces it step by step.

The session core is a synchronous state machine without threads, sockets, clocks or allocation of its own resources at run time: bytes and the current time go in, bytes and events come out. Transports are plug-ins around it. Equal inputs at equal times give equal bytes and events in every port. Only the ephemeral keys of an encrypted session are drawn at random; a test seed makes them deterministic as well.

Principles

  • A payload is the encoding of one record or message of a route’s root, produced and read by the schema writer and reader. The session decodes no payload; it only converts the states of a topic between full records and deltas.
  • Both sides hold the same network declaration bound with the same parameter values. The handshake compares hashes and closes the session on any difference.
  • Data from the peer is untrusted. Every limit is known before a packet is read; a violation closes the session with a code, never with a crash.
  • Time is a monotonic Int64 count of microseconds, the unit of the host clock. The core never reads a clock.

Declaration

A network declares the routes of one client–server pair:

The schema grammar reads it:

Routes are separated by commas or line breaks; repeated and trailing separators are allowed. Each route stays on one line.

  • Side. client routes go from the client to the server, server routes the other way.
  • sends names a schema, a message or a message set with a wire role. Its class is reliable or bulk.
  • publishes names a schema with a wire role, a topic. Its class is latest or reliable.
  • at most every stands only on publishes and states the shortest interval between two updates of the topic. Its value is a time quantity, written as a literal or a constant, greater than zero and at most 3600s. It is rounded up to whole microseconds. The session itself does not enforce it; generated code exposes it as a constant.
  • A side names a root at most once per verb.
  • A network holds 1 to 64 routes. The position of a route, counting from 0, is its route index; its channel on the wire is the index plus 1.

A network shares the namespace of schemas, messages, message sets and tag sets. It is no type: a field or another route cannot name it. Code generation alone accepts it as a root and writes its constants and typed functions. A root may be abstract nowhere in a network.

Code Condition
schema.unknownName a route names no declared schema, message or message set, or a rate names no constant of its file
schema.invalidRoute a route names a declaration of the wrong kind or without a wire role, an abstract schema, a class its verb does not take, a rate on sends, or a rate that is no time, not positive or above 3600s
schema.duplicateRoute a side names the same root twice with the same verb
schema.tooLarge a network has more than 64 routes

Binding

Binding a network binds every route root with the same parameter values; the parameters of all roots must be given. A bound network holds, per route, the bound root and its largest encoding, and the network hash.

Network hash

The network hash is FNV-1a 64, as for the schema hash, over this canonical form: UTF-8 lines, each ending with one line feed, tokens separated by one space.

One route line follows per route in route order. <class> is reliable, latest or bulk; <rate> is the interval in microseconds as a decimal integer, 0 without a rate; <binding hash> is the root’s binding hash as 16 lowercase hexadecimal digits. Classes, rates, order, names and parameter values thus all change the network hash.

Sessions

A session connects one client and one server. Each side runs one connection, the state machine of this document. A server runs one connection per client.

  1. The client sends hello with its network hash, the binding hash of every route, its limits, the compressions it accepts and the host’s token, sealed when the session is encrypted.
  2. The server checks the protocol and the hashes. On a difference it closes the session with network.protocolMismatch or network.schemaMismatch. Otherwise it reports the event connecting with the token, and the host accepts or refuses the client.
  3. On acceptance the server sends welcome and reports connected; the client reports connected when it receives welcome. Refusal closes with network.refused and the host’s detail.
  4. Both sides then exchange data packets until one side sends close, the transport ends, an error closes the session or the peer stays silent for the timeout.

A client sends nothing but hello and close before welcome; a server sends nothing but retry, welcome and close before acceptance. Either receiving anything else is network.malformed. On a datagram transport the handshake repeats lost packets and the server validates the client’s address first; the datagram handshake adds those rules. A server with a key answers a hello that is not sealed with a retry that carries its public key; encryption adds those rules.

Delivery classes

Class Delivery
reliable every message, complete, in the order sent across all reliable routes of the direction
latest the newest message per route; a message not yet started is replaced by a newer one
bulk every message, complete, in the order sent across all bulk routes of the direction, after all other traffic; each message is a transfer

Transmission order within a packet is: reliable, then latest, then the tick frame, then bulk; cancel frames precede them all. A reliable or bulk message is sent completely before the next one of its class starts; messages of different classes interleave in fragments. On a stream or message transport a latest message, once started, is completed; a newer message of the same route then waits in its place and is itself replaceable. On a datagram transport a newer message starts once the current one is sent, and the receiver drops an older incomplete one (latest messages on datagrams).

Sending

A side sends a payload on its sends routes and publishes one on its publishes routes, the topics. Both return a status and never throw; the checks apply in table order:

Status Meaning
invalidRoute the route index is out of range, or the route is not sent by this side with this verb
notConnected the connection is not Connected
notSubscribed a published topic of the server is not subscribed
messageTooLarge the payload is longer than the route root’s largest encoding; on a bulk route also longer than the transfer limit of either side
queueFull the reliable queue would exceed its byte limit; on a bulk route, 8192 transfers are queued, the new transfer id would be 8192 ahead of the oldest one whose cancel the peer has not confirmed on a datagram transport, or the queued bulk bytes plus the payload would exceed the transfer limit of either side
queued the message is queued

A latest message never makes the queue full; it replaces the waiting one.

Topics

A topic is a publishes route. Its messages are states: each one is a full record of the topic’s schema, and the receiver gets the full record. On the wire a state travels as a full record or as a delta against an earlier state the receiver has confirmed, whichever is shorter.

Subscriptions. The server decides which client receives which of its topics. A server connection starts with none of them subscribed; the host subscribes and unsubscribes a topic per connection, and publishing on a topic that is not subscribed reports notSubscribed. Both are usage errors on a client connection and for a route that is no topic the server publishes, and do nothing when the state does not change. Subscribing sends nothing by itself; the host publishes the current state when it wants the client to start with it. Unsubscribing drops the waiting latest state of the topic and the sender’s ring; a latest state already started is completed and reliable states already queued are sent. The topics a client publishes are always subscribed.

Numbering. Every state has a number modulo 65536. A latest state’s number is its message id, taken when its first fragment is sent; a latest state replaced before it started gets no number. Reliable states are numbered from 0 per topic in the order they are published. The receiver takes the same numbers: the message id of a latest state and its own count of the reliable states of the topic.

Rings. Each side holds a ring of states with their numbers per topic and direction. When a state enters it, the oldest states leave while the ring holds more than 32 states or more than the baseline limit of full record bytes, but the newest state always stays. The baseline limit is the smaller of the limits both sides announce in the handshake.

Sending a state. Its base is the newest state of the sender’s ring that is confirmed. On a stream or message transport a state is confirmed when the packet carrying its last fragment is acknowledged, and an acknowledgement confirms every packet up to the sequence it names. On a datagram transport a reliable state is confirmed when every byte of its message is acknowledged, and a latest state when a confirmation frame of the receiver names it. The sender writes a delta against the base when there is one, the delta encoding succeeds, and the delta is shorter than the full record; otherwise the full record. Then the state enters the ring.

Receiving a state. The receiver takes the base from its ring, decodes the delta against it and reports the full record; a full record is reported as received. The state then enters the receiver’s ring. The receiver’s ring always still holds the base: it received the base and, after it, only states that also entered the sender’s ring since, so the states from the base on fit the same limits. On a datagram transport the receiver of a latest topic skips states that were lost or overtaken; it then holds fewer states after the base, which fit the limits all the more.

Ticks

Since: 0.6.0

A tick is a set of latest topic states that one side publishes as one state of its world. The receiver reports a tick only when it holds every state the tick names, and then reports them together, so it never sees a new World beside an old World_Cards.

Publishing. A side opens a tick, publishes the states of its members and closes it. While a tick is open, a publish on a latest topic the side publishes makes the state a member of the tick; include makes the topic a member with its last published state without publishing it again, and does nothing when the topic is a member already. Reliable topics, sends and transfers are never members and pass unchanged while a tick is open. A second publish of a member in one tick replaces its first state. Closing a tick reports notConnected on a connection that is not connected, which drops the tick, and otherwise queued; an empty tick sends nothing. Opening a tick while one is open, closing or including without an open tick, including a topic that has no published state and including a route that is no latest topic the side publishes are usage errors. On a server a topic that the connection has not subscribed is no member there.

Numbering. One tick is in transmission at a time; a closed tick waits behind it. A waiting tick is replaced by a newer one: each of its members becomes a latest state that the newer tick’s state of the same topic replaces, and the newer tick names the states of its own members. Ticks are numbered per direction from 0 modulo 65536 when their tick frame is first written; a replaced tick gets no number.

Sending. A tick starts when no earlier tick is in transmission. A published member then becomes the topic’s waiting latest state. An included member names the topic’s newest state when the receiver holds it and no newer state of the topic waits: on a stream or message transport the newest completely sent state, on a datagram transport a confirmed one. Otherwise the tick publishes the topic’s last published state again, as a delta against the confirmed base or as the full record. With no confirmed state at all every member therefore travels as a full record, and a tick never depends on a state lost earlier. A member state that is dropped before it starts leaves the tick; a tick left without members ends. The sender writes the tick frame after the last fragment of every state it names. A tick whose members are all held by the receiver sends only the tick frame, and the receiver reports only the tick event; a host uses it to move its timeline on while the world rests.

Receiving. A state whose mode byte marks it as a tick member enters the receiver’s ring as usual but is not reported on arrival. The receiver holds it until its tick is reported or a newer member state of the route replaces it; held states count toward the pending received bytes. The receiver holds at most one incomplete tick. A tick frame whose number is 1 to 32767 ahead of the held tick, or of the last reported tick when none is held, replaces the held one; any other is ignored. When the receiver holds every state that the held tick names — held, last reported or in the ring — it reports, in route order, a message event for each member whose named state is newer than the last state it reported on that topic, followed by one tick event with the tick number.

Datagram delivery. A packet with a tick frame asks for acknowledgement. A lost tick frame is sent again while its tick is the newest one in transmission and no newer tick started.

Rates. A tick is published as often as the host closes ticks. at most every of a member stays advice to the host, as for single states.

Mixing. A topic may be published alone and as a member of ticks on the same connection. A state published alone is reported on arrival; the receiver then counts it as the last reported state of that topic.

Transfers

A message on a bulk route is a transfer: data of up to the transfer limit, sent with its size and hash, compressed when that is shorter, and cancellable without closing the session.

Sending. A transfer gets its id when it is queued: the next number of the bulk numbering, which the host reads from the connection right after send. The sender computes the SHA-256 hash of the data and, when both sides accept Deflate and the data is not empty, compresses it with the reference encoder. The compressed form is sent when it is shorter than the data, otherwise the data itself. The message is:

Field Encoding
compression 1 byte: 0 none, 1 Deflate
size varint of up to 64 bits, the length of the data
hash 32 bytes, SHA-256 of the data
data the data, or its raw Deflate stream (RFC 1951)

The size varint follows the varint rules with up to ten bytes; a value above 64 bits is not canonical.

Receiving. The receiver checks a complete transfer in this order and cancels it with the code, without reporting it, when a check fails:

Check Code
the message is empty or its size varint cannot be read network.transferCorrupt
the size exceeds the receiver’s transfer limit or the route root’s largest encoding network.transferTooLarge
the compression is unknown, or Deflate while the receiver does not accept it network.transferCorrupt
fewer than 32 bytes follow the size network.transferCorrupt
uncompressed data whose length differs from the size, or compressed data at least as long as the size network.transferCorrupt
the Deflate stream is invalid or does not yield exactly the size network.transferCorrupt
the hash of the data differs network.transferCorrupt

A transfer that passes is reported as message with the data and the transfer’s id. A message frame of a bulk route whose total exceeds the receiver’s transfer limit, limited by the route root’s largest encoding, plus 43 header bytes is network.messageTooLarge. Bulk bytes pending at the receiver count toward their own limit of twice the transfer limit plus 86 instead of the pending received bytes; exceeding it is network.queueFull.

Progress. Both sides report transferProgress with the route, the id, the bytes and the total of the transfer’s message, header included. The receiver reports the bytes it holds whenever a frame adds bytes; the sender reports the bytes the peer acknowledged: on a stream or message transport the written bytes up to the end of each acknowledged packet that is one of the last 256 data packets it sent, on a datagram transport the acknowledged bytes of the transfer. A progress event replaces the newest pending event when that reports the same transfer, so a host that takes events late sees one event with the latest count. The receiver’s message follows its last progress event.

Cancelling. The sender’s host cancels a queued transfer by its id with an optional code, network.transferCancelled when it gives none, as long as not every byte was sent once; afterwards, for an id no queued transfer of the route carries and on a connection that is not connected the cancel reports false and changes nothing. A route this side does not send as bulk or an invalid code is invalidArgument. Cancelling sends a cancel frame to the receiver, also for a transfer not yet started, and reports transferCancelled locally. The receiver cancels a transfer that fails a check the same way. A cancelled transfer sends no further bytes, keeps its id, and reports neither progress nor message; the session continues.

On a stream or message transport the sender writes the cancel frame in queue order: in place of a transfer not yet started, and before the rest of a started one. The receiver then accepts a cancel only for the transfer in progress or, when none is, for the next id; any other is network.malformed. On a datagram transport cancel frames are sent at once and resent until acknowledged. The receiver takes the id as a frame of the bulk class of datagram delivery: it ignores a cancel for an id it already reported, skipped or cancelled, an id outside that window is network.malformed, and it marks a transfer ahead of it cancelled, so the next transfers are reported without it. A received cancel reports transferCancelled with the peer’s code once per transfer and stops the sender’s transfer when it is still queued.

Deflate

The reference encoder writes one final block with the fixed Huffman code (BFINAL 1, BTYPE 01) and greedy matches; the end-of-block symbol follows the last symbol and the last byte is padded with zero bits. Both ports produce the same bytes for the same data.

  1. Two tables of 32768 entries hold chain heads and links. Every head starts at none; links are written before they are read. The hash of position p is ((d[p] << 10) xor (d[p+1] << 5) xor d[p+2]) and 32767. Inserting p with at least three bytes from p on stores the head of its hash as the link at p and 32767 and makes p the head; a position with fewer bytes is not inserted.
  2. At position p with at least three bytes left the encoder walks the chain from the head of p’s hash, at most 32 candidates, stopping before a candidate more than 32768 bytes back. It compares each candidate with p up to the smaller of 258 and the bytes left; a longer match replaces the best one, the first of equal length stays, and a match of the full length ends the walk. The next candidate is the link stored at the current candidate’s slot.
  3. A best match of at least 3 bytes is written as length and distance and every position it covers is inserted; otherwise the byte at p is written as a literal and inserted. The encoder continues after the written bytes.

Every Deflate stream (RFC 1951) of any block types is accepted when it ends with its final block, yields exactly the size and leaves no byte after the final block’s last byte. Code tables that zlib rejects are invalid: over-subscribed lengths, and incomplete ones except a single literal or distance code of length 1. The fixture conformance/fixtures/Network/deflate.json holds the reference encoder’s output and accepted and rejected streams.

Limits

Each connection has receive and send limits. The defaults are fixed values of this document; the host may change them per connection.

Since: 0.6.0 — derived limits

A limit the host leaves unset whose default below names a need takes the larger of its default and that need, at most 1073741824, so a bound network never exceeds a default limit by its own largest message. A value the host sets applies unchanged. The needs are the largest encodings of the roots of the bound network:

  • pending received bytes: the largest message this side receives on a route that is not bulk, with the mode byte of a topic message;
  • queued reliable bytes to send: the largest root of a reliable route this side sends, with the mode byte of a topic message;
  • baseline limit: the largest root of a topic;
  • transfer limit: the largest root of a bulk route.
Limit Default Exceeded
largest packet received and sent, 1200 to 65535 bytes; 0 selects the default 16384; 1200 on a datagram transport network.packetTooLarge
baseline limit: full record bytes of a topic’s ring, 0 to 1073741824 65536, or the need older states leave the ring
pending received bytes: incomplete messages and undelivered events, without bulk, 1 to 1073741824 4194304, or the need network.queueFull
transfer limit: data of one transfer sent and received, 0 to 1073741824 67108864, or the need status messageTooLarge; network.transferTooLarge
frames received per second, token bucket of one second, 1 to 1000000 4096 network.rateExceeded
queued reliable bytes to send, 1 to 1073741824 1048576, or the need status queueFull
timeout without a received packet, 0 to 1 h, 0 for none 10 s network.timeout
keepalive after the last sent packet, 0 to 1 h, 0 for none 1 s
delay of an acknowledgement, 0 to 1 h 10 ms
send budget in bytes per second, 0 to 1073741824, 0 for none 0 sending waits

A message is longer than its route allows when its total length exceeds the largest encoding of the route’s bound root, plus the mode byte of a topic message: network.messageTooLarge. A side sends packets no larger than the smaller of its own packet limit and the peer’s announced one, and transfers no larger than the smaller transfer limit. Deflate is used only when both sides accept it. A value outside its range is invalidArgument.

At most 65536 events wait untaken; any further event other than closed closes the connection with network.queueFull. Taken events free their place.

At most 65536 reliable messages wait to be sent, also before the handshake, whatever their length; a further send or publish on a reliable route reports queueFull. A message frees its place once it is sent, on a datagram transport once it is acknowledged.

The frame bucket starts full with as many frames as the limit and refills with the limit per second, counted in exact integer steps of one microsecond. On a datagram transport a frame is accepted only while the bucket holds one. On a stream or message transport the bucket limits what the receiver takes in instead: received bytes are accepted while it holds at least one frame, and every frame of a packet they complete draws one frame, also below zero. A packet with more frames than the limit closes the connection, and so do bytes passed while the bucket holds less than one frame. The connection reports whether it takes further bytes, and its next deadline includes the time at which the bucket holds a frame again. A host leaves the received bytes unread until then, so the transport’s flow control slows the sender. The send budget is a bucket of at most the send packet size that starts full, also when a budget replaces none, and refills with the budget per second; a data packet with frames is sent only while the bucket is not negative and is then subtracted in full, an encrypted packet with its type byte and tag. hello, welcome, close and data packets without frames ignore the budget. The host may change the budget at any time, for example from the measured round-trip time; this is the congestion hook.

Acknowledgement and keepalive

Every data packet carries a sequence number, 0 for the first and then one higher per packet modulo 65536, and from the first received data packet on an acknowledgement: the newest received sequence and a bit for each of the 32 sequences before it, bit 0 for the sequence one older, set when that sequence was received. A data packet with at least one message, cancel or tick frame, a keepalive and a probe ask for acknowledgement and set flag bit 1; a packet that only acknowledges or confirms does not, so acknowledgements never answer each other. A message, cancel or tick frame in a packet that does not ask is network.malformed. An asking packet is acknowledged by the next data packet, which a side sends at the latest after the acknowledgement delay. A side that has sent nothing for the keepalive interval sends a data packet without frames, the keepalive.

The round-trip time is measured when an acknowledgement names a newer sequence than before and that packet asked for acknowledgement and is one of the last 256 data packets the side sent: the sample is the time since that packet was sent. It includes the peer’s acknowledgement delay. The first sample sets the estimate; each later one moves it by an eighth of the difference, in integer arithmetic that truncates toward zero.

On a stream or message transport packets arrive complete and in order, so nothing is resent, a data packet must carry exactly the next sequence, and an acknowledgement must name a sequence the receiver has sent and not be older than the previous one. A datagram transport follows datagram delivery instead.

Datagram delivery

On a datagram transport each packet travels alone and may be lost, duplicated, delayed or reordered. The sender keeps what is not acknowledged and resends what is lost; the receiver ignores what it has already and restores the order of each class. Loss detection follows QUIC (RFC 9002) in integer microseconds; every division truncates toward zero.

Receiving data packets. A data packet whose flags and sequence are valid is placed by its distance to the newest received sequence modulo 65536: 1 to 32767 ahead makes it the newest; up to 32 behind is received when its bit is not yet set. The first data packet is received with any sequence. A packet with the newest sequence, a set bit or a sequence more than 32 behind is a duplicate or too old and is ignored without reading further; it still counts as a received packet for the timeout.

Acknowledging. An asking packet makes an acknowledgement due after the acknowledgement delay, as on other transports, and at once when 16 asking packets have arrived since the last data packet this side sent.

Sent packets. The sender records its last 1024 data packets: the send time, whether the packet asked, and the fragments of messages it carried. A fragment names its message and the range of bytes it carried. A packet that does not ask is settled when sent; an asking packet stays outstanding until it is acknowledged or lost. Only an outstanding packet needs its fragments again, so the recorded fragments are those from the oldest outstanding packet among the last 1023 sent on, at most 16384. While the packet 1024 before the next one is still outstanding, the send window is full: no frame is due, and a data packet is written only for an acknowledgement, the keepalive or a probe. Before such a packet is written, that outstanding packet is declared lost, so its fragments are due again. A packet ends before a message frame whose fragment would exceed 16384 recorded fragments.

Acknowledgements received. The newest sequence of an acknowledgement names the newest packet sent with that sequence: with n packets sent, the packet n − 1 − ((n − 1 − sequence) mod 65536), counted from 0. Naming a packet before the first, or any packet before one was sent, is network.malformed. The named packet and each packet a set bit names, counting back from it, are acknowledged when they are recorded and outstanding; acknowledging a packet acknowledges its fragments. A packet already acknowledged or declared lost stays as it is, so every range of bytes is outstanding in at most one packet.

The round trip is sampled as on other transports when the named packet is newer than every packet acknowledged before and asked for acknowledgement. Besides the estimate a side keeps the variation and the newest sample. The first sample sets the variation to half the sample; each later one moves it by a quarter of the difference between the absolute difference of estimate and sample and the variation, computed before the estimate moves. Until the first sample, loss detection uses an estimate and a newest sample of 333000 µs and a variation of 166500 µs.

Loss detection. The largest is the newest packet acknowledged. An outstanding packet older than the largest is lost when it is at least 3 packets older, or when its loss delay has passed since it was sent: nine eighths of the larger of estimate and newest sample, at least 1000 µs. Detection runs after every acknowledgement received and when the earliest loss delay of an outstanding packet older than the largest ends. Lost packets are handled in packet order; their fragments are queued to be resent in that order.

Probe timeout. While a packet is outstanding and no outstanding packet older than the largest awaits its loss delay, the probe timeout counts from the last asking packet sent: the estimate, plus the larger of four times the variation and 1000 µs, plus the local acknowledgement delay, doubled for each expiry since an acknowledgement last acknowledged an outstanding packet, at most 10 times. On expiry the side sends a probe: a data packet that asks even when no frame is due.

Reliable and bulk messages. Each class sends its messages in order as on other transports; a message keeps its place in the send queue and counts toward the queue limit until every byte of it is acknowledged, and the queue head leaves then. At most 8192 messages per class are started and still queued; the next one waits. A cancelled transfer leaves the queue at once; its lost fragments are not resent. Until the peer confirms its cancel frame, its id stays open: a new transfer whose id would be 8192 or more ahead of the oldest open id, queued or cancelled, is queueFull. In a packet each class first resends the ranges of its lost fragments in the order they were lost, then continues with new fragments. A range that does not fit the packet is split; its rest waits. A message of total 0 is acknowledged when its one frame is.

The receiver accepts a frame of a class whose id is 0 to 8191 ahead of the next message of the class to report, modulo 65536; an id up to 8192 behind is a duplicate and ignored, and any other id is network.malformed. The frames of one id arrive in any order; they must name the same channel and total, else network.malformed. Bytes of a range received already keep their first value. A message counts its total toward the pending received bytes from its first frame, before the receiver reserves memory for it, and a cancelled transfer frees its memory at once, so the pending limits bound the memory of incomplete messages; memory kept for reuse stays within the same limits. Complete messages are reported in id order: a message complete before an earlier one waits for it.

Packet order. A data packet carries owed confirmation frames first, then lost and new cancel frames, then reliable resends and new reliable fragments, then per latest route its resends, its current message and a newer one, then the tick frame, then bulk resends and new bulk fragments.

Latest messages on datagrams

A newer message of a latest route starts as soon as every fragment of the current one is sent once; the current one is then no longer sent. A lost fragment of a latest message is resent only while that message is still the route’s current one and no newer message waits; otherwise it is dropped.

The receiver holds at most one incomplete message per latest route. A frame of the message in progress continues it. A frame whose id is 1 to 32767 ahead of the message in progress, or ahead of the last reported message of the route when none is in progress, drops the message in progress and starts a new one; before the first message every id is ahead. A frame of the message in progress with another total is network.malformed. Any other frame is ignored. A latest message counts its total toward the pending received bytes from its first frame and is reported when complete.

Confirmation frames

On a datagram transport the receiver of a latest topic confirms states for the sender’s base. When a state of a latest topic enters the receiver’s ring, the receiver owes the sender one confirmation frame for it; a newer state of the same route replaces a confirmation not yet sent. A data packet carries all owed confirmations first, in route order. They are never resent, do not ask for acknowledgement, so a data packet with only confirmations does not ask, and ignore the send budget; an owed confirmation makes a data packet due like a received asking packet.

Field Encoding
channel varint 0
kind 1 byte 0
topic varint, the channel of the topic’s route
number 2 bytes, the state’s number

A confirmation counts toward the frame limit. One whose topic is not a latest topic the receiving side publishes is network.malformed; one that names a state no longer in the ring is ignored.

Datagram handshake

  • The client sends hello and repeats it while no welcome arrives: after 1 s, then after twice the previous interval each time. Without welcome it closes with network.timeout like any connection, so loss can fail the handshake.
  • A retry received in the state Hello after the first hello was sent stores its cookie when the cookie is not empty, takes its key as encryption allows, and the client sends hello at once; the interval starts again at 1 s. Any other retry is ignored.
  • A server in AwaitAccept ignores hello; a server in Connected answers each hello with the same welcome bytes it sent first. In both states it does not read the hello.
  • The client accepts the first welcome it can read in the state Hello and ignores data packets before it and every welcome after it. Its hello repetitions are identical, so any welcome answers the hello it holds. An encrypted welcome answers only the hello that holds the same ephemeral key: when a late retry changes the cookie after the server accepted the earlier hello, the client cannot read its welcome and the handshake ends on the timeout.
  • A side sends close once; when it is lost, the peer closes on its timeout.

Address validation

A server answers a client it does not know without keeping state, so a forged source address gains no connection and at most as many bytes as it sent. A gate holds a secret key of 32 bytes and a window length, and checks each datagram of an unknown address:

Result Condition Server action
drop the datagram is not a hello, is shorter than 1200 bytes, has a wrong magic, or its fields up to the cookie cannot be read within the bounds of a hello ignore it
retry the cookie is empty or not valid send the gate’s 27-byte retry
accept the cookie is valid create a server connection and pass it the datagram

Reading the fields within the bounds means: the version varint, the 8 bytes of the network hash, a route count from 1 to 64 with its hashes, the four limit varints and a cookie of at most 64 bytes. The connection checks the version and the rest.

A cookie is 24 bytes: the window number as 8 bytes, signed, the current time divided by the window length rounded toward negative infinity, followed by the first 16 bytes of HMAC-SHA256 with the key over the four bytes GESC (47 45 53 43), the window number’s 8 bytes and the address. A cookie is valid when its window number is the current or the previous one and its HMAC bytes match, compared in constant time. The address is the client’s address as the transport gives it; the socket transports use the 4 or 16 bytes of the IP address followed by the port as 2 bytes, most significant first. The retry holds type 2, the varint 24, a fresh cookie for the current window and the varint 0, no key; the gate holds no server key.

Timeout and closing

A connection closes with network.timeout when no packet has arrived for the timeout, counted from its creation, also during the handshake.

The host closes a connection with a detail text; the code is network.closed. Closing drops all queued messages and queues one close packet; the connection reports closed at once. An error found in received data closes the same way with its code and sends it to the peer. A received close reports closed with the peer’s code and detail. When the host reports the end of the transport, the connection reports closed with network.transportClosed unless it has closed already. After closed a connection ignores received data and sends nothing beyond its close packet.

Wire format

Values

Integers of fixed width are little-endian. A varint is unsigned LEB128 of a value that fits 32 bits: seven bits per byte, least significant group first, the high bit set on every byte but the last. It takes at most five bytes and is canonical: a last byte of zero is allowed only as the single byte of the value 0. Anything else is network.malformed. Text is a varint length and that many bytes.

Packets

A packet’s first byte is its type. A packet is read completely; bytes left over after its last field are network.malformed, and so is an unknown type.

Type Packet
1 hello

On a datagram transport zero bytes follow the token up to at least 1200 bytes in all; a shorter datagram hello or another byte after the token is network.malformed. A connection does not check the cookie; the gate does.

A wrong magic or version is network.protocolMismatch, checked before anything else. A different route count or network hash is network.schemaMismatch. Its detail names the root of each route of the server whose binding hash differs or which the client lacks, in route order and separated by , ; it names the network when no root differs. Both are checked before the security byte, so they close without encryption.

A retry with neither a cookie nor a key, with a cookie on a stream or message transport, or received by a server is network.malformed; so is a retry on a stream or message transport beyond the one a client accepts.

Frames

Field Encoding
channel varint, route index plus 1
message id 2 bytes
offset varint, the position of the chunk in the message
total varint, the length of the message

A message is sent in one frame or, when it does not fit, in fragments of consecutive offsets. The sender fills each packet: a fragment takes the largest chunk that fits the remaining space. Channel 0 is a control frame.

Reliable messages are numbered from 0 per direction across all reliable routes, bulk messages likewise across bulk routes, and latest messages per route; the number wraps from 65535 to 0. A reliable or latest message takes its number when its first fragment is sent; a bulk message, a transfer, when it is queued.

The receiver checks each message frame. The first three checks apply on every transport; on a datagram transport datagram delivery replaces the others:

  • a channel beyond the route count is network.malformed; a route the peer does not send is network.unexpectedRoute;
  • a total beyond the route’s largest encoding is network.messageTooLarge;
  • a chunk of length 0 in a message of nonzero total, or a chunk ending beyond the total, is network.malformed;
  • a frame at offset 0 starts a message; its id must be the next of its numbering, and no message of its class may be in progress (for latest: of its route);
  • a frame at a later offset continues the message in progress of its class (for latest: of its route) with the same channel, id and total, at the offset where the previous chunk ended;
  • anything else is network.malformed.

A message is complete and reported when its chunks reach its total.

Control frames

A frame on channel 0 is a control frame; a kind byte follows the channel. Kind 0 is a confirmation frame, valid only on a datagram transport. Kind 2 is a tick frame. Kind 1 is a cancel frame of a transfer:

Field Encoding
channel varint 0
kind 1 byte 1
route varint, the channel of the transfer’s bulk route
transfer id 2 bytes
code text of 1 to 64 bytes from ! to ~

A cancel names a route the sender of the transfer sends; the receiver of the transfer sends one back for a transfer that failed a check. A cancel sent back for an id the sender has not given a transfer yet, while its ids have not wrapped around, is network.malformed. Another kind, a route that is not a bulk route, or a malformed field is network.malformed. On a datagram transport a packet with a cancel frame asks for acknowledgement, and a cancel frame in a packet that does not ask is network.malformed. Control frames count toward the frame limit.

Topic messages

A message of a topic starts with a mode byte:

Mode Rest of the message
0 the full record
1 to 32 a delta against the state that many states before this one in the topic’s numbering

Bit 0x80 of the mode byte marks a state of a latest topic as a tick member; the low seven bits keep the modes above.

The receiver closes with network.malformed when a topic message is empty, its mode without the tick bit is above 32, the tick bit is set on a reliable topic, its base is not in the ring, or the delta does not decode against the base or leaves bytes over.

Transports

  • Stream (TCP): each packet is preceded by its length as a canonical varint. A length of 0 is network.malformed, a length above the packet limit network.packetTooLarge.
  • Message (WebSocket, in-process): one binary message per packet. A packet above the packet limit is network.packetTooLarge.
  • Datagram (UDP over IPv4 or IPv6): one datagram per packet. A packet above the packet limit is network.packetTooLarge, an empty one network.malformed. The server passes the datagrams of an unknown address through address validation and those of a known address to its connection. A socket transport may drop datagrams when its receive queues are full, as the network could.

The client of a stream or WebSocket transport opens the connection; the WebSocket endpoint path is chosen by the host. A text WebSocket message closes with network.malformed.

Encryption

A server with a key of its own encrypts its sessions with the cipher suite. The server’s key is a static X25519 key pair; each session adds an ephemeral key pair on each side. The client learns that only the holder of the server’s key can read the session; the server learns nothing about the client but its token. The data of a session is secret and authentic and stays secret when the server’s key is disclosed later; the token stays secret only as long as the server’s key does.

GesNetwork assumes that the client receives the server’s public key from outside the protocol, for example with its build or its configuration. It neither signs nor distributes keys.

Security levels

A session reaches one of three levels:

Level Meaning
none not encrypted
encrypted encrypted with a server key that the client received in a retry; protects only against attackers who read but do not change packets, for development and local networks
verified encrypted with the server key that the client was given in advance, its pinned key

A connection’s level is none until it is connected. A server reports encrypted for every encrypted session, because it cannot tell whether the client pinned its key.

Since: 0.6.0 — client and server security

The client’s options hold its security; a client without one is a usage error. Its first hello, its answer to a retry with a key and the lowest level it reaches follow it:

Client security First hello retry with a key Lowest level
pinned, with the server public key of 32 bytes sealed with the pinned key its key is ignored verified
development key request the client takes the key and sends a sealed hello encrypted
none plain, with the token the client takes the key and sends a sealed hello none

A client without a pinned key takes the key of each retry that carries one, so a key from a later retry replaces an earlier one: until a welcome authenticates, any of them may be forged. On a stream or message transport a client accepts one retry, only in answer to a hello that is not sealed, and only with an empty cookie and a key; any other retry there is network.malformed. On a datagram transport the datagram handshake processes a retry in the state Hello after the client sent its first hello and ignores it otherwise.

The server’s options hold its security, a key of its own or none; a server without a security is a usage error. A server checks the protocol and the hashes of every hello first and closes a difference without encryption. Then:

  • A server with a key answers a plain hello and a key request with a retry that holds an empty cookie and its public key and stays in AwaitHello. It never accepts a plain hello.
  • A server without a key closes on a key request or a sealed hello with network.insecure.
  • A server with a key opens the token of a sealed hello; when the token does not authenticate, it closes with network.authenticationFailed.

A client reads welcome in the form its hello asks for, plain or sealed. A sealed welcome that does not authenticate is ignored on a datagram transport and closes the session with network.authenticationFailed on the others.

Ephemeral keys

A client draws an ephemeral private key for each sealed hello whose bytes differ from the previous one; repeating a hello sends the same bytes again. A server draws one when it reads a sealed hello whose token authenticates. A private key is 32 bytes from the system’s cryptographic random generator; X25519 clamps it.

For tests and golden bytes only, a connection may instead derive its ephemeral keys from a test seed: the n-th key of the connection, counted from 0, is SHA-256("GESK" ‖ side ‖ seed ‖ n), with side the byte 0 for a client and 1 for a server and the seed and n as 8 bytes each. Such keys are known to everyone who knows the seed; the API marks the option as insecure.

Handshake keys

Extract(salt, ikm) and Expand(prk, info, length) are the two steps of HKDF with SHA-256. Labels are ASCII bytes without a terminator. S is the server’s public key, the pinned one or the one the client took, s its private key; ce and CE are the client’s ephemeral private and public key, se and SE the server’s.

  1. The client computes es = X25519(ce, S) and the server es = X25519(s, CE).
  2. Both derive hello_key = Expand(Extract(S, es), "ges hello", 32). The token is sealed with ChaCha20-Poly1305 under hello_key with a nonce of 12 zero bytes. Its additional data is the hello from the type byte through the token’s length varint, so it covers the cookie; the token’s length is the plaintext’s length plus 16.
  3. On acceptance the server computes ee = X25519(se, CE) and the client, on welcome, ee = X25519(ce, SE). Both compute the transcript T, SHA-256 of the hello from its type byte through the token’s last byte, without padding, followed by SE, and prk = Extract(T, es ‖ ee).
  4. welcome_key = Expand(prk, "ges welcome", 32) seals the welcome fields with a nonce of 12 zero bytes. A sealed welcome is the type byte 3, SE, the sealed fields and the tag; its additional data is the type byte and SE.
  5. The client’s secret is Expand(prk, "ges client", 32), the server’s Expand(prk, "ges server", 32). Each side seals with its own secret and opens with the peer’s.

An X25519 result of 32 zero bytes closes the session with network.authenticationFailed. Each key seals one plaintext only: a hello with other bytes has a fresh CE.

Sealed packets

From Connected on, each side of an encrypted session sends only sealed packets, both data and close:

Field Encoding
type 1 byte, 6
sequence 2 bytes, the packet number modulo 65536
sealed packet the inner packet sealed, then the tag of 16 bytes

The inner packet is a data packet without its sequence, type byte 5 included, or a close packet. Another inner type is network.malformed. The additional data is the 3 bytes of type and sequence. A sealed data packet is 17 bytes longer than its plain form; the packet limit applies to the sealed packet.

Each side numbers its sealed packets from 0 per direction; a close takes the next number, and a data packet’s sequence is the low 16 bits of its number. A sender does not check the number against 2^62: even a million packets per second take more than 100000 years to reach it. A direction’s key changes every 2^24 packets without a signal:

  • iv = Expand(secret, "ges iv", 12)
  • key = Expand(secret, "ges key" ‖ epoch, 32), with epoch = number >> 24 as 8 bytes
  • nonce = iv XOR (number as 8 bytes ‖ 4 zero bytes)

The receiver reconstructs the number. On a stream or message transport it is the count of sealed packets received before. On a datagram transport it is the number closest to the expected number with the same low 16 bits, with the expected number one above the largest authenticated number, 0 before the first, as RFC 9000 appendix A.3 decodes it; a candidate at or above 2^62 is not chosen. The receiver keeps the keys of the epochs next to that of the largest authenticated number, so a forged packet never causes a key derivation.

A packet is authenticated before it changes any state. One that does not authenticate is dropped on a datagram transport, without counting as received for the timeout; on the other transports it closes the session with network.authenticationFailed.

Before welcome the server closes without encryption, refusals included, so their detail is not protected. A client accepts a plain close until it has read a sealed welcome; a server accepts one until it has authenticated a sealed data packet, because the client closes without encryption until it reads the welcome. After that a plain packet is dropped on a datagram transport, without counting as received for the timeout, and is network.malformed on the others. A plain data packet on an encrypted session and a sealed packet on a session that is not encrypted are never valid.

Replayed hellos

The server cannot tell a replayed sealed hello from a new one; it reports connecting with the token again. Whoever replays it lacks ce and can neither read nor send in the resulting session. On a datagram transport a replay must come from the client’s address while its cookie is valid; on the other transports it may come from anywhere. Hosts should therefore use single-use or short-lived tokens, tokens bound to a time, and grant rights only at the client’s first message, which proves the client holds ce.

Cipher suite

The suite is X25519, ChaCha20-Poly1305 and HKDF-SHA256. Every port produces the same bytes; a port may use a platform implementation of a primitive, such as CryptoKit, swift-crypto, .NET or libsodium, and keeps its own implementation for platforms without one. conformance/fixtures/Network/crypto.json holds the vectors both ports and every platform implementation must reproduce; scripts/test-network-crypto.py checks them against an independent oracle.

  • X25519 follows RFC 7748, section 5: the scalar is clamped, bit 255 of the u-coordinate is masked, the Montgomery ladder runs 255 steps with conditional swaps and the result is encoded canonically. A public key is the scalar multiplied with u = 9.
  • ChaCha20-Poly1305 follows RFC 8439, section 2.8, with a 32-byte key, a 12-byte nonce and the 16-byte tag after the ciphertext.
  • HKDF follows RFC 5869 with HMAC-SHA-256 (RFC 2104, FIPS 180-4); SHA-256 also computes the transcript and test-seed keys.

Implementations run in constant time with respect to secrets. X25519 uses no branch and no memory index that depends on the scalar or the result, and fixed iteration counts for field arithmetic and inversion. Poly1305 compares the tag over all 16 bytes without an early exit; opening releases no plaintext and changes no buffer when the tag does not match. Checking a shared secret for zero combines all 32 bytes before branching. Test vectors do not establish these properties; reviews of the code do.

Security

A session that is not encrypted neither hides nor authenticates anything: the token is shown to whoever can read the transport and the peer’s identity is not proven. Such a session belongs on a transport that protects both, such as TLS; a browser client uses WebSocket only over wss. The in-process transport and TLS need no encryption of their own; their hosts give both sides the security none.

An encrypted session hides and authenticates every packet after welcome and the token. It does not hide the hello and retry fields, a plain welcome, a close before welcome, or the size and timing of packets. At the level encrypted an attacker who can change packets can read the session; only verified proves the server. The protocol never proves the client; the token does.

An attacker who can drop or forge packets can always prevent a session or end it early: on a datagram transport through lost packets, forged retry packets or a forged plain close during the handshake. Address validation proves only that the client receives at its address.

API

Since: 0.6.0

The core is the package GameEventScript.Network (C#, netstandard2.1) and GameEventScriptNetwork (Swift, without Foundation). It depends only on Runtime. The socket transports are the separate packages GameEventScript.Network.Sockets (C#, .NET 8, TcpListener, WebSocket.CreateFromStream and Socket for UDP) and GameEventScriptNetworkSockets (Swift, SwiftNIO). The public API owns the member names per port.

A socket listener holds at most 64 clients that wait for the host or still run their WebSocket upgrade. Accepting pauses while it holds them all; a validated UDP hello beyond them is dropped, and the client sends it again. One IP address holds at most 8 of these clients: the listener closes its further TCP and WebSocket sockets and drops its further UDP hello packets. A client the host takes frees its place.

A socket session hands its socket about 256 KiB of packets that are not yet written and then stops. Further packets wait in the connection, so a peer that reads slowly fills the connection’s send queue and send reports queueFull. The close packet of a closed connection passes that bound, so closing always reaches the socket.

A TCP or WebSocket session passes received bytes only while its connection takes them. The rest waits in about 64 read chunks, and then the session stops reading, so the peer’s sending slows down; a session reports the end of its transport after the last chunk. A UDP session passes every datagram; one longer than its receive buffer closes a known client’s connection with network.packetTooLarge and is dropped otherwise.

A TCP or WebSocket session that closes in order first writes its last packets, then ends its sending: TCP by closing its sending half, WebSocket with a close frame, which also answers the peer’s close frame. It then reads and drops received bytes until the peer’s end, for at most 10 s, before it closes the socket, so the peer reads the last packets instead of a reset. A TCP connect fails after 10 s, and so does a WebSocket upgrade, on the listener as on the client and there with the TLS handshake of wss.

An insecure test key seed derives a connection’s ephemeral keys from a known value, so anyone who knows it reads the session; it exists only for tests and golden bytes. The socket listeners and connects refuse options and connections that use it.

A host drives a connection like this:

  1. Create a client connection with the bound network, the token and the current time, or a server connection with the bound network and the current time.
  2. Pass every received packet or stream chunk with the current time; on a stream or message transport leave them unread while the connection takes no further bytes.
  3. Take events until none is left; accept or refuse a connecting client.
  4. Send and publish, directly or through the typed functions of generated code, and on the server subscribe and unsubscribe topics.
  5. Take packets to transmit into a buffer until none is left. The buffer holds at least 1200 bytes; a smaller one is a usage error.
  6. Call advance with the current time no later than the connection’s next deadline, then take packets again.

Ends

Since: 0.6.0

An end owns connections and their transports and drives them from one call, so a host does not write the drive loop of API itself. A client end holds one connection; a server end holds an acceptor and every accepted connection. Ends are synchronous and threadless in the core; the socket packages add connectors, acceptors and a wait.

Creating. A client end takes the bound network, a connector, the options and a token; a server end takes the bound network and an acceptor. Both take a clock. A connector opens a client transport: in-process as one side of a pair or, in the socket packages, TCP, WebSocket or UDP with host and port. An acceptor hands over the transports of new clients. Creating starts no I/O; the first poll connects or accepts.

Polling. poll reads the current time from the end’s clock and then, in this order, accepts waiting clients, passes every received packet to its connection, takes events until none is left and hands each to the caller’s handler, and transmits every due packet. A handler may send, publish, open and close ticks and close connections; the packets this produces leave in the same poll. A handler that polls its own end again is a usage error. When the handler closes the connection whose event it handles, or refuses the client, the end skips that connection’s remaining events of the poll up to its disconnect event. poll never blocks and never calls the handler outside its own call. The next deadline of an end is the earliest time at which a poll has work without new input: the current time before the first poll and after a send, publish, tick close or close outside a poll, else the earliest deadline of its connections.

Sending before the handshake. A client end keeps sends, publishes and ticks made before connected and passes them to the connection when it connects: reliable and bulk messages in order, the newest state of each latest route and the newest closed tick. The kept reliable bytes obey the connection’s send queue limit, and the kept transfers its limits for queued transfers against this side’s transfer limit, each counted uncompressed with its header; a send that does not fit reports queueFull. A kept transfer beyond the transfer limit the server announces keeps its place in the transfer ids and is cancelled at once with network.transferTooLarge. Closing drops what is kept.

Server. The server end accepts a connecting client after its event unless the handler accepted or refused it, also when the handler throws. Each client gets a stable end-local id, which events carry and per-client calls take; an unknown id is a usage error. By default the server end subscribes every connected client to every topic it publishes; the host can turn that off when it creates the end and subscribes and unsubscribes topics per client at any time. publish and ticks reach every connected, subscribed client; send without a client reaches every connected client. Both report messageTooLarge when the payload exceeds the limits of some client, and then no client receives it, else queueFull when the queue of some client is full, and then the others received it. The server end keeps the last published state of each latest topic: a tick that includes a topic gives a client that has not received that state the state itself, so a client that joined later holds the complete world after its first tick. A client that connects while a tick is open joins it. A closed client leaves the end after its clientDisconnected event.

Events. An end reports the events of its connections, named by side, and adds received:

End event Data
connecting server: client id and token
connected client: the reached security level
clientConnected server: client id and the reached security level
disconnected client: code, detail and whether the peer closed
clientDisconnected server: client id, code, detail and whether the peer closed
message client id on the server; route index and payload, borrowed until the handler returns
tick client id on the server; tick number
transferProgress, transferCancelled client id on the server; as the connection’s events
received the last event of every poll that reported at least one message or tick

After received every state of the latest complete tick and every message of the poll has been reported, so a host commits its view there.

Closing. close closes the client’s connection, one client’s or every client’s with a detail; the close packets leave with the next poll. Releasing an end releases its transports once the packets already handed to them have left; a released end cannot be polled.

Isolation. An end belongs to one caller at a time, like a Host, and is not thread-affine. Swift ends are not Sendable; poll takes a non-escaping closure, which inherits the caller’s isolation, so an end lives inside a @MainActor type or any actor and its handler reads that actor’s state directly. C# Poll<THandler>(ref THandler handler) calls a struct handler without allocating; a class handler works through the same interface.

Waiting

Since: 0.6.0

The socket packages wait on an end until one of its sockets has input or its next deadline passes, whichever comes first, without polling: C# WaitAsync and a blocking Wait, Swift wait() async. The core has no wait.

Pairs

Since: 0.6.0

A pair is a client end and a server end connected in one process without sockets, by the message transport with the in-process options unless the host gives others. Its two modes:

  • realtime uses the system clock; packets reach the other end at its next poll, and the ends connect while they poll.
  • synchronous uses one virtual clock starting at 0 that only the pair moves. Creating the pair runs the handshake; the server accepts the client without a connecting event, and both ends report their connected events on their first poll. Every send, publish, tick close, close and poll on either end runs both connections until no packet moves, so what one end sends is reported by the other end’s next poll. Acknowledgements are not delayed: the pair runs with an acknowledgement delay of 0. Timers — keepalive, timeout and resending — fire only when the host advances the pair’s clock; the handshake, sending and delivery never need it. Advancing a realtime pair, or a pair while one of its ends is polled, is a usage error.

In both modes a packet waits in the pair while the receiving connection takes no further bytes, in a synchronous pair until the host advances the clock far enough to refill the frame bucket. While 64 packets wait for it, the sending connection keeps its further packets, as with a socket whose peer stops reading; only the close packet of a closed connection still leaves.

Simulated network

The simulated network connects a client and a server connection in one process with seeded latency, deterministic in every port. It draws from the random generator created from its seed. Each packet is delayed by the base latency plus a draw from 0 to the jitter inclusive, but never arrives before a packet sent earlier in the same direction, so order is preserved. Equal seeds, options and inputs give equal packets, events and times. A packet for a stream or message connection that takes no further bytes arrives at the time its frame bucket holds a frame again, whatever other deadlines the connection has, and the packets behind it wait too. While 64 packets are under way to such a connection, the sender keeps its further packets as in a pair; a deadline it has reached that needs a packet, such as a keepalive, waits with them until the connection takes bytes again.

Between datagram connections the simulated network may also lose, duplicate and reorder packets, with a loss and a duplicate rate in per mille, 0 to 1000, and reordering on or off. For each packet it draws the delay; with a loss rate above 0 a number from 0 to 999 that loses the packet when below the rate; then, for a packet not lost and a duplicate rate above 0, a number from 0 to 999 that adds a copy when below the rate, and the copy’s delay. With reordering a packet or copy arrives after its own delay, not held behind packets sent earlier; packets due at the same time arrive in the order sent, a packet before its copy. Loss, duplicates and reordering require both connections to use the datagram transport.
